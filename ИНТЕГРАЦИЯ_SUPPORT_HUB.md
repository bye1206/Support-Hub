# Интеграция Support Hub ↔ RAG-Оркестратор

**Версия:** 1.1 (2026-11-18)
**Для:** разработчики Support Hub
**От:** команда RAG-ассистента техподдержки

---

## 1. Общая схема

Support Hub выступает в роли клиента — точно так же, как продовый канал (CraftTalk/КТ).
Оркестратор **не** вызывает Support Hub: вся коммуникация инициируется вызовами Support Hub.

```
Support Hub ──► POST /api/v1/chat            — создание чата
Support Hub ──► POST /api/v1/message/{id}    — вопрос пользователя
Support Hub ◄── JSON-ответ с answer          — ответ ИИ или триггер-код
```

Внутри оркестратора: pre-processing (детекция сервисов, PII, short-circuit) →
RAG (поиск по базе знаний + LLM) → post-processing (валидация ответа).

---

## 2. Базовые параметры

| Параметр | Значение |
|---|---|
| Базовый URL | `http://10.9.79.252:8000` |
| Проверка доступности | `GET /health` → `{"status":"ok",...}` |
| Таймаут ответа | **до 120 сек** (внутренний таймаут RAG = 115 с). Клиентский таймаут ставьте ≥ 120 с |
| Формат | HTTP, JSON (UTF-8) |

---

## 3. Заголовки (обязательные)

| Заголовок | Обязателен | Значение | Назначение |
|---|---|---|---|
| `X-API-Key` | да | выдаём отдельно | Аутентификация, пробрасывается в RAG-API |
| `X-User-Id` | да | например `supporthub-test-001` | Идентификатор пользователя/теста |
| `X-Source` | **да** | `support-hub` | **Критично:** помечает трафик как тестовый. Без него трафик пойдёт в общую прод-статистику |
| `Content-Type` | да | `application/json` | |

---

## 4. Эндпоинт 1 — создание чата

```http
POST /api/v1/chat
```

Тело запроса:
```json
{"title": "support-hub-test"}
```

Ответ (прозрачное проксирование в RAG-API, формат RAG-API):
```json
{"id": 12345, "title": "support-hub-test", ...}
```

Из ответа нужен `id` (целое число) — это `chat_id` для всех последующих сообщений.

---

## 5. Эндпоинт 2 — сообщение (основной)

```http
POST /api/v1/message/{chat_id}
```

`{chat_id}` в пути — числовой идентификатор из п. 4.

Тело запроса:
```json
{"query": "как подключить сетевой диск R:?"}
```

Успешный ответ — **HTTP 201**:
```json
{
  "id": 0,
  "chatId": 12345,
  "query": "как подключить сетевой диск R:?",
  "answer": "Для подключения сетевого диска R: выполните ...",
  "sources": null,
  "rating": null,
  "createdAt": "2026-11-18T08:00:00.123456Z",
  "updatedAt": "2026-11-18T08:00:00.123456Z"
}
```

Возможные нестандартные ситуации:
- Пустой `query` → запрос проксируется как есть (ответ в том же формате);
- `answer` может быть **триггер-кодом** — см. раздел 6;
- RAG недоступен → HTTP 503, тело `{"detail":"RAG-API unavailable"}` — рекомендуем
  показать пользователю «сервис временно недоступен» и не ретраить автоматически
  чаще 1 раза.

---

## 6. Триггер-коды в answer (КРИТИЧНО)

Поле `answer` иногда содержит НЕ текст, а короткий служебный код (~11 символов,
латиница/цифры). Support Hub **обязан** интерпретировать их так же, как это делает
продовый канал:

| Код | Значение | Что должен сделать Support Hub |
|---|---|---|
| `tY7Ve077FyZR1` | «вызвать оператора» | Перевести диалог на оператора (стандартный процесс Support Hub) |
| `hnQRDemsuPZY` | «помогло» (подтверждение действия ИИ) | Отметить как решённое |

Коды могут появиться в любой момент диалога (пользователь сам попросил оператора,
ИИ не нашёл информацию, технический сбой и т.д.). Правило: `answer` длиной ≤ 30
символов, состоящий из латиницы и цифр, следует проверять на совпадение с кодами
выше. Значения кодов согласованы и не меняются без уведомления.

## 7. Пример жизненного цикла (smoke-тест)

```bash
BASE=http://10.9.79.252:8000
KEY=<выданный X-API-Key>

# 0. Доступность
curl -s $BASE/health

# 1. Создать чат
CHAT=$(curl -s -X POST $BASE/api/v1/chat \
  -H "X-API-Key: $KEY" -H "X-User-Id: supporthub-test-001" \
  -H "X-Source: support-hub" -H "Content-Type: application/json" \
  -d '{"title":"support-hub-test"}')
# → взять .id

# 2. Задать вопрос
curl -s -X POST $BASE/api/v1/message/$CHAT \
  -H "X-API-Key: $KEY" -H "X-User-Id: supporthub-test-001" \
  -H "X-Source: support-hub" -H "Content-Type: application/json" \
  -d '{"query":"не работает Outlook"}'
# → взять .answer

# 3. Просьба оператора (должен вернуться код tY7Ve077FyZR1)
curl -s -X POST $BASE/api/v1/message/$CHAT \
  -H "X-API-Key: $KEY" -H "X-User-Id: supporthub-test-001" \
  -H "X-Source: support-hub" -H "Content-Type: application/json" \
  -d '{"query":"оператор"}'
```

## 8. Что важно знать при тестировании

1. **Изоляция статистики**: весь трафик с `X-Source: support-hub` пишется в
   отдельное хранилище и **не попадает** в продовую аналитику/дашборд.
2. **База знаний продовая**: тестовые вопросы проходят по той же базе знаний,
   что и реальные пользователи. Просим избегать массовой автоматической нагрузки
   (без согласования) — она искажает продовые метрики и создаёт нагрузку на LLM.
3. **Реальные действия**: если ИИ выполнит действие (сброс пароля и т.п.),
   оно будет реальным. Не отправляйте такие запросы без необходимости.
4. PII в вопросах маскируется на нашем конвейере, но лучше не слать в тестах
   реальные персональные данные.
5. Ожидаемое время ответа: 3–30 с обычные вопросы; до 120 с в сложных случаях.

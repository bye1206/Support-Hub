# Integration Contract: RAG Assistant Gateway (external version)

**Version:** 1.0 · **Date:** 2026-11-09
**Audience:** platform developers (new chat platform team)
**Scope:** how to call the assistant gateway (RAG orchestrator layer) —
endpoints, auth, payloads, timing, errors, trigger codes, migration notes.

> Anonymized external version. Internal hostnames replaced with placeholders;
> the real base URL and API key are provided separately by the integration team.

---

## 1. Overview

The gateway sits between the chat platform and the LLM backend. The platform
makes **synchronous** HTTP calls and receives a finished answer in the
response. **There are no webhooks/callbacks** — the gateway never calls back.

```
Chat platform (yours)          Gateway (ours)                 LLM backend
        │  POST /api/v1/chat           │                              │
        │ ───────────────────────────► │  proxy ────────────────────► │
        │  201 {id, ...}               │  ◄────────────────────────── │
        │ ◄────────────────────────────│                              │
        │  POST /api/v1/message/{id}   │                              │
        │ ───────────────────────────► │  pre-processing   (≤ 3 s)    │
        │         waits 30–60 s        │  query ────────────────────► │
        │                               │  ◄────────────────────────── │
        │                               │  post-processing  (≤ 3 s)   │
        │  201 {answer, ...}            │                              │
        │ ◄────────────────────────────│                              │
```

Latency expectations:

| Case | Time |
|------|------|
| Typical answer (LLM) | ~30–60 s (avg ≈ 50 s) |
| Hard upper bound | 120 s — gateway always answers before this |
| Fast path (fixed phrases, trigger codes, mass-incident texts) | 0–1 s |
| **Required client-side HTTP timeout** | **≥ 130 s** |

## 3. Authentication

Two headers on **every** request:

| Header | Required | Description |
|--------|----------|-------------|
| `X-API-Key` | yes | project API key, issued by the integration team (one key per platform) |
| `X-User-Id` | yes | end-user identifier, arbitrary string (e.g. employee ID). Used for chat isolation and logging. The platform is responsible for correctness. |
| `Content-Type` | yes | `application/json` |

No OAuth, no sessions, no per-request tokens.

## 4. Endpoints

### 4.1 `POST /api/v1/chat` — create a chat

Request body:

```json
{ "title": "Support request" }
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `title` | string | no | ≤ 255 chars |

Response `201 Created`:

```json
{
  "id": 42,
  "projectId": 30,
  "endUserId": "employee-123",
  "title": "Support request",
  "createdAt": "2026-11-09T12:00:00Z",
  "updatedAt": "2026-11-09T12:00:00Z"
}
```

Keep `id` — it is the `chat_id` used in 4.2.

### 4.2 `POST /api/v1/message/{chat_id}` — send a message, get the answer

Request body:

```json
{ "query": "VPN does not connect" }
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `query` | string | **yes** | user message text |
| `sources` | object | no | **accepted and ignored** |
| `metadata` | object | no | **accepted and ignored** |

> Send **only `query`**. Conversation history is NOT sent by the platform —
> the gateway maintains its own context.

Response `201 Created`:

```json
{
  "id": 0,
  "chatId": 42,
  "query": "VPN does not connect",
  "answer": "**In short:** reset the VPN profile.\n1. ...",
  "sources": null,
  "rating": null,
  "createdAt": "2026-11-09T12:00:30.123456Z",
  "updatedAt": "2026-11-09T12:00:30.123456Z"
}
```

| Field | Type | Notes |
|-------|------|-------|
| `id` | int | **dummy value (always 0)** — the real message ID is assigned by the backend; do NOT rely on it, do not store it as a unique key |
| `chatId` | int | echo of the request |
| `query` | string | echo of the original user message (unmodified) |
| `answer` | string | the bot's answer, **Markdown** (bold, lists, links), UTF-8. Check it for trigger codes (section 7) |
| `sources` | null | reserved, always null for now |
| `rating` | null | reserved |
| `createdAt` / `updatedAt` | string | ISO 8601 UTC with `Z`, e.g. `2026-11-09T12:00:30.123456Z` |

## 5. Timing & timeout contract

| Parameter | Value |
|-----------|-------|
| Average LLM answer | ~50 s |
| Gateway internal LLM timeout | 115 s |
| Platform-side hard limit (current platform) | 120 s |
| **Your HTTP client timeout** | **≥ 130 s** (recommended) |

If the LLM backend is unavailable or too slow, the gateway does **not**
return 500/504 — it returns `201` with `answer` = the **operator trigger
code** (section 7), so the user is handed to a human agent within the same
request.

---

## 6. Errors & retry semantics

HTTP status codes:

| Code | Meaning | Platform action |
|------|---------|-----------------|
| `201` | success | render `answer` (after trigger-code check) |
| `401` | bad or missing API key | check `X-API-Key` |
| `403` | access denied | check key permissions, contact integration team |
| `404` | chat not found | create a new chat |
| `422` | validation error | check body (`query` missing/empty type) |
| `503` | LLM backend unreachable | show an error to the user; retry is possible |

Retry rules:

- The gateway makes **one** LLM call per message. No automatic retries, no
  backoff, no queueing.
- **There is no idempotency.** A retried `POST` with the same `query` creates
  a **new** message in the chat (the LLM may answer differently).
- Safe retry strategy for the platform: on `503`/network error show a local
  "try again" hint; on timeout (> your limit) show an error — do NOT
  silently re-POST.
- Duplicate messages are visible to the user in chat history — avoid
  double-sends (double-click protection on the client side).

## 7. Trigger codes (critical)

The bot may answer with a **short code** instead of text. Codes are
alphanumeric, ≤ 30 chars, no spaces, and always contain at least one digit.
Your platform MUST detect them and act:

| Code | Event | Required platform action |
|------|-------|--------------------------|
| `hnQRDemsuPZY` | "resolved" — the user confirmed the problem is solved | close the dialog / run satisfaction survey |
| `tY7Ve077FyZR1` | "operator" — escalate to a live agent | hand the conversation to a human operator |

How codes appear in practice:

1. The user types a magic word ("помогло" / "оператор") → the gateway returns
   the code **instantly** (no LLM call, 0–1 s).
2. The LLM itself decides the dialog is finished → the message `answer` is
   the code.

Detection recipe (mirrors the gateway's guards):

```python
def is_trigger_code(answer: str) -> bool:
    a = answer.strip()
    return len(a) <= 30 and " " not in a and a.isalnum() and not a.isalpha()
```

Codes are configured on the gateway side and can be rotated; the integration
team will provide the new values in advance if that happens.

---

## 8. Answer content

- Format: **Markdown** (Telegram-safe: special chars `*`, `[`, etc. are
  pre-escaped where needed). Render as Markdown or strip to plain text.
- Encoding: UTF-8. Language: Russian.
- No HTML, no images, no attachments in the answer.
- Fixed fast-path answers (greetings/farewells, mass-incident notices) come
  as plain text in the same envelope.

---

## 9. What you do NOT need to send

- conversation history — gateway keeps its own context;
- user profile beyond `X-User-Id`;
- anything besides `query` in the message body.

## 10. Minimal integration checklist

- [ ] `POST {base}/api/v1/chat` with `X-API-Key`, `X-User-Id`
- [ ] `POST {base}/api/v1/message/{chat_id}` with the same headers
- [ ] HTTP client timeout ≥ 130 s
- [ ] handle `201` → render `answer` (Markdown)
- [ ] handle trigger codes `hnQRDemsuPZY` / `tY7Ve077FyZR1`
- [ ] handle `401/403/404/422/503` per section 6
- [ ] no reliance on message `id`; no history sending; no double-sends

## 11. curl examples

```bash
BASE="https://<gateway-host>"        # real URL provided by integration team

# 1) create chat
curl -X POST "$BASE/api/v1/chat" \
  -H "X-API-Key: $API_KEY" \
  -H "X-User-Id: employee-123" \
  -H "Content-Type: application/json" \
  -d '{"title": "Support request"}'
# → 201 {"id":42,"projectId":30,"endUserId":"employee-123",...}

# 2) send message (wait up to 130 s)
curl --max-time 130 -X POST "$BASE/api/v1/message/42" \
  -H "X-API-Key: $API_KEY" \
  -H "X-User-Id: employee-123" \
  -H "Content-Type: application/json" \
  -d '{"query": "VPN does not connect"}'
# → 201 {"id":0,"chatId":42,"query":"...","answer":"...","createdAt":"..."}
```

## 12. Migration notes (replacing the current platform)

- The gateway is platform-agnostic: the only things the new platform needs
  are the base URL + a fresh `X-API-Key` + `X-User-Id` mapping for its users.
- Chat IDs from the old platform are **not** portable (they live in the LLM
  backend); users start fresh chats after cutover.
- Suggested cutover: point a small % of traffic to the new platform, compare
  answer quality/latency for 1–2 weeks, then full switch. The gateway keeps
  full per-message logs (latency, status, triggers) for the comparison.
- Integration testing window and test API key — to be arranged with the
  integration team.

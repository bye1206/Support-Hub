## 3. Непереговорные продуктовые правила

- **Одно обращение пользователя = один тикет = один логический диалог.** Не предлагай дробить одно обращение на несколько тикетов. Несколько проблем в одном обращении остаются в одном тикете.
- Один тикет связан с одним логическим диалогом; у диалога может быть несколько трёхчасовых сессий.
- Сессия длится ровно 3 часа от создания. Это не idle timeout и активность не продлевает её.
- Истечение сессии не закрывает тикет и не закрывает диалог.
- После `CLOSED` следующее обращение начинает новый тикет и новый диалог.
- Продолжение той же проблемы после `RESOLVED` возвращает прежний тикет в `OPEN`.
- После ответа оператора тикет переходит в `PENDING_USER`; после нового сообщения пользователя — в `OPEN`.
- SLA продолжает отсчитываться в `PENDING_USER`.
- После Human Handoff ИИ больше не обрабатывает новые сообщения этого диалога в MVP. Автоматического возврата к ИИ нет.
- Support Hub — источник истины и владелец полной истории сообщений. AI Orchestrator не является владельцем истории.
- Mattermost Bot сохраняется как транспортный адаптер. Не заменяй его без отдельного решения.
- RAG, Pre-process, Post-process и AI Orchestrator остаются отдельной существующей внутренней разработкой. Не переносить их внутрь Support Hub.
- Внутренние заметки операторов не являются публичными сообщениями и не отправляются пользователю или ИИ автоматически.

## 4. Архитектурные ограничения

- Архитектура: модульный монолит, не набор микросервисов.
- Backend: Python + FastAPI.
- БД: PostgreSQL.
- ORM: SQLAlchemy 2.x; миграции Alembic.
- Схемы и валидация: Pydantic v2.
- Redis для временного состояния/присутствия/координации и очередей согласно выбранной реализации.
- Фоновые задачи: worker; ARQ — предпочтительный кандидат, но окончательный выбор нужно проверить и зафиксировать.
- Frontend: React + TypeScript.
- Файлы: MinIO.
- Авторизация операторов: Keycloak OIDC через корпоративный LDAP/AD.
- On-premise развертывание; Docker Compose для MVP, Nginx как reverse proxy.
- Tag — корпоративный мессенджер на базе Mattermost.

Не добавляй Kafka, Kubernetes, микросервисы, отдельные базы для каждого модуля или другие тяжёлые компоненты без обоснованной необходимости и согласования.

## 5. Интеграции

### Tag / Mattermost

- Tag присылает сообщения на webhook callback существующего бота.
- Текущий payload содержит `team_id`, `team_domain`, `channel_id`, `channel_name`, `timestamp`, `user_id`, `user_name`, `post_id`, `text`, `file_ids`.
- Бот принимает callback и передаёт нормализованное событие в Support Hub.
- Исходящие ответы Support Hub возвращаются через существующего бота, который использует свою текущую реализацию отправки в Tag.
- Токен Tag принадлежит существующему боту; не переносить его в Support Hub без отдельного согласования.
- Первый пример с алертами из другого проекта (fire-and-forget, `@all`, timeout 5 секунд, редактирование алертов) не является требованиями Support Hub.
- Tag Bot Webhook API — корпоративное расширение, описанное пользователем. Не утверждай, что это стандартная функция Mattermost.
- Стандартные Mattermost endpoints для постов/файлов можно использовать только после проверки прав, версии и особенностей инсталляции Tag.
- Не предполагай callback authentication, retry semantics или timestamp units: они остаются открытыми вопросами.
- Фильтруй собственные сообщения бота и системные события, чтобы не создавать циклы; точные поля payload надо подтвердить.

### AI Orchestrator

- Предлагавшиеся endpoints и JSON-контракты являются проектными, не подтверждёнными существующими API.
- Перед реальной интеграцией исследуй текущий контракт Orchestrator и сделай адаптер.
- Support Hub передаёт текущий запрос и необходимую историю, сформированную из собственной БД.
- Оркестратор возвращает ответ, Human Handoff или техническую ошибку.
- Проверяй режим и версию состояния диалога при приёме результата.

## 6. Инженерные требования

- Сначала осматривай существующий репозиторий. Не перезаписывай его файлы без проверки.
- Не создавай огромный объём кода за один проход. Разбивай работу на маленькие вертикальные этапы.
- Сначала предложи план и критерии приёмки; затем реализуй согласованный этап.
- Используй типизацию, явные схемы, dependency injection и разделение API / services / repositories.
- Не помещай бизнес-логику в FastAPI route handlers.
- Все изменения схемы БД — через Alembic. Не используй `create_all()` как production-миграции.
- Не используй SQLite как замену PostgreSQL для проверки специфичных ограничений, ENUM, JSONB, partial indexes и конкурентных транзакций.
- Тестируй реальные ограничения PostgreSQL и конкурентные сценарии.
- Для исходящих сообщений используй транзакционный Outbox. Понимай, что сеть даёт at-least-once, а не магическое exactly-once; проектируй идемпотентность и сверку неопределённых результатов.
- Входящие webhook должны быть идемпотентны по внешнему ID события.
- Используй `Decimal` для денежных значений, если они появятся; не используй float для точных величин.
- Храни время в UTC (`TIMESTAMPTZ`), отображай с учётом настроенного timezone.
- Не логируй токены, пароли, полные секретные payload, содержимое файлов или лишние персональные данные.
- Проверяй авторизацию на backend для каждого endpoint. Скрытие кнопки во frontend не является защитой.
- Не открывай MinIO публично; выдавай контролируемый доступ к файлам.
- Все важные действия оператора должны попадать в аудит.

## 7. Проверки

После изменений запускай применимые проверки и сообщай точные результаты:

- Backend: pytest, Ruff, mypy/Pyright (после появления конфигурации).
- Frontend: lint, typecheck, tests, build (после появления конфигурации).
- DB: Alembic upgrade/downgrade на тестовой PostgreSQL, проверка индексов/FK.
- Integrations: тесты на idempotency, retry, timeout, duplicate callbacks и stale AI responses.

Не утверждай, что проверки пройдены, если команды не запускались.

- Не придумывай контракт Tag или AI Orchestrator.
- Не трактуй проектные примеры JSON как реальные контракты внешних систем.
- Не превращай открытые вопросы в тихие допущения.
- Если неизвестное не блокирует задачу, запиши допущение в `docs/DECISIONS.md` с пометкой `PROPOSED`.
- Если неизвестное влияет на безопасность, целостность данных, миграцию или внешний контракт — остановись и запроси решение.
- При обнаружении противоречий между документами сообщи об этом и предложи исправление; не выбирай вариант молча.

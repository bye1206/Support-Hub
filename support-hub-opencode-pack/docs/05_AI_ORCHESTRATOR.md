# 05. Интеграция с AI Orchestrator

## 1. Границы

Существующий AI Orchestrator и его Pre-process, RAG, Post-process остаются отдельным внутренним контуром. Support Hub не должен переносить в себя эти компоненты.

Support Hub отвечает за:
- сохранение пользовательского сообщения;
- формирование контекста из собственной истории;
- создание AI processing run;
- запуск внешней обработки;
- приём результата;
- сохранение AI-ответа в `messages`;
- отправку ответа пользователю;
- переключение на оператора при Handoff.

Orchestrator отвечает за обработку полученного запроса и возвращает результат.

## 2. Предлагаемая модель обмена

Предпочтительная модель — асинхронная:

1. Support Hub отправляет запрос в Orchestrator.
2. Orchestrator быстро подтверждает приём.
3. Выполняет Pre-process/RAG/Post-process.
4. Отправляет callback в Support Hub.

Проектные варианты endpoints:
- Support Hub → Orchestrator: `POST /api/v1/ai/process`;
- Orchestrator → Support Hub: `POST /api/v1/integrations/ai/events`.

Это НЕ подтверждённые существующие endpoints. Перед реализацией нужно получить реальный контракт и адаптировать его.

## 3. Минимальные идентификаторы

Нужно согласовать передачу:
- `request_id` — ID запуска, выданный Support Hub;
- `event_id` — уникальный ID callback-события;
- `correlation_id` — сквозная корреляция;
- `conversation_id` — внутренний ID диалога;
- `conversation_state_version` — версия состояния на момент запроса;
- `input_message_id` — ID сообщения Support Hub;
- `external_run_id` — необязательный ID запуска Orchestrator.

Orchestrator не должен самостоятельно менять тикет или диалог в Support Hub.

## 4. Контекст

Support Hub сам выбирает предыдущие публичные сообщения из `messages` и формирует контекст.

Не дублировать полную историю в таблице `ai_processing_runs`.

Не передавать внутренние заметки автоматически.

Текущая input message передаётся отдельно от предыдущих context messages, чтобы избежать повторения.

Нужно согласовать стратегию ограничения размера контекста, формат вложений и доступ к ним.

## 5. События результата

Предлагаемые типы:
- `AI_RESPONSE` — результат для пользователя;
- `HUMAN_HANDOFF` — просьба передать оператору;
- `AI_PROCESSING_FAILED` — техническая ошибка.

Реальные enum и payload нужно сопоставить с существующим Orchestrator.

## 6. Защита от гонок

- AI runs для одного диалога обрабатываются последовательно в MVP.
- На диалог допускается не более одного активного run в состояниях SENT/PROCESSING.
- При Handoff Support Hub транзакционно меняет режим диалога и state version.
- Поздний callback со старой версией не публикуется пользователю.
- Результат помечается `STALE` либо отменяется в соответствии с причиной.
- После Handoff Orchestrator не получает новые пользовательские сообщения этого диалога.

Системно нельзя гарантировать отмену уже отправленного сетевого ответа; нужно исключить публикацию устаревшего результата на стороне Support Hub и Bot как можно ближе к отправке.

## 7. Открытые вопросы

Нужны реальные примеры:
- endpoint запуска обработки;
- JSON request;
- синхронный/асинхронный режим;
- callback schema;
- формат Handoff;
- формат ошибок;
- request/run ID;
- идемпотентность;
- передача изображений/файлов;
- текущая логика контекста/истории.

Не реализовывать выдуманный контракт вместо существующего API.

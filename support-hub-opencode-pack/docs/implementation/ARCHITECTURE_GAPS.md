# Противоречия, пробелы и риски архитектуры

Дата: 2026-11-09. Источники: `docs/00–13`, `AGENTS.md`. Формат: **G-xx** — противоречие/пробел, **R-xx** — риск. Статусы: OPEN (нужно решение владельца), PROPOSED (есть предложение, ждёт подтверждения — см. `TECH_DECISIONS.md`).

## A. Противоречия между документами

### G-01. Ссылка на несуществующий файл в AGENTS.md — OPEN
`AGENTS.md` §8: «запиши допущение в `docs/DECISIONS.md`». Такого файла нет; реестр решений — `docs/12_DECISION_LOG.md`. Предложение: исправить ссылку на `docs/12_DECISION_LOG.md` (и/или на `docs/implementation/TECH_DECISIONS.md`) при первом коммите. Не влияет на бизнес-логику, но ломает навигацию агентов.

### G-02. Пакет не распакован в корень репозитория — OPEN
`README.md` требует распаковать пакет в корень нового Git-репозитория, фактически всё лежит в `support-hub-opencode-pack/`, Git не инициализирован. Пока не решено, любой `git init` / bootstrap будет «плавающим». Предложение в `TECH_DECISIONS.md` (P-01).

### G-03. Статус тикета после AI-ответа не определён — OPEN (влияет на модель)
Подтверждено только: «ответ **оператора** → `PENDING_USER`» (D-011, `01` §3). Что делает с тикетом ответ **ИИ** — нигде не зафиксировано: тикет остаётся `NEW`? переходит в `OPEN`? Проблема связана с открытым `NEW → OPEN` (11.D.1, D-033 PROPOSED). Пока нет решения, TicketService не реализуем полностью (этап 4).

### G-04. Длительность сессии: подтверждённая константа vs конфигурируемая переменная — OPEN
D-007 подтверждает «ровно 3 часа, не idle timeout». `docs/03` §3 задаёт CHECK `expires_at = started_at + interval '3 hours'` — а `.env.example` вводит `CONVERSATION_SESSION_DURATION_SECONDS=10800`. CHECK в БД не может ссылаться на конфиг приложения: либо длительность фиксирована в коде/DDL (рекомендую, тогда переменную убрать), либо CHECK упрощается до `expires_at > started_at`. Сейчас документы дают взаимно несовместимые указания. Предложение — P-03.

### G-05. Расхождение этапной сетки roadmap и стартового ТЗ — INFO
`docs/10` разделяет SLA (этап 10) и hardening/деплой (этап 11); стартовый промпт объединяет их в один этап 10. В `IMPLEMENTATION_PLAN.md` сохранена сетка из 10 этапов, SLA оформлен подфазой 10a. Противоречия по существу нет, зафиксировано для прозрачности.

## B. Пробелы (правила не определены)

### G-06. Маршрутизация входящего сообщения в тикет — OPEN, критично для этапа 5
Нигде не задано правило: входящее DM пользователя из Tag — это **продолжение** существующего тикета, **reopen** `RESOLVED` (D-010) или **новое обращение** (после `CLOSED`). «Продолжение той же проблемы» — термин оператора, а не алгоритма. Без правила нельзя строить ingress и MessageService. Предложение — P-04 (маршрутизация к последнему незакрытому тикету пользователя). В `11_OPEN_QUESTIONS.md` этого пункта нет — пробел в самом реестре вопросов.

### G-07. Поведение при технической ошибке AI — OPEN
`05` §5 определяет событие `AI_PROCESSING_FAILED`, но не определяет, что происходит дальше: ретрай, служебное сообщение пользователю, автоматический Human Handoff, тишину. В `11_OPEN_QUESTIONS.md` (блок B) спрашивается только формат ошибок от Orchestrator, но не доменное поведение Support Hub. Нужен продукт-решение до этапа 6.

### G-08. Матрица прав OPERATOR / SUPERVISOR / ADMIN отсутствует — OPEN, блокирует этап 7
`07` §2 задаёт три роли одной фразой каждая. Какие действия доступны SUPERVISOR, а какие ADMIN (переназначение чужих тикетов? изменение SLA-политик? повтор FAILED Outbox?) — не формализовано. `11.D.3` спрашивает про переназначение, но не про матрицу целиком. Backend RBAC без матрицы не реализовать.

### G-09. Механизм истечения сессий не выбран — PROPOSED
`01` §2 фиксирует *что* (по истечении `EXPIRED`), но не *как*: фоновый worker переводит статусы (eager) или статус вычисляется при чтении и запись делает worker (lazy). Влияет на workers этапа 4. Предложение — P-05.

### G-10. Аллокация `sequence_no` не описана — PROPOSED (технический выбор)
Уникальность `(conversation_id, sequence_no)` задана (`03` §3), порядок отображения по `sequence_no` задан (`06` §3), но механизм конкурентной аллокации счётчика (внутритранзакционный `UPDATE conversations ... RETURNING last_message_sequence + 1`) не описан. Влияет на этапы 3–4.

### G-11. Enforcement «не более одного активного AI run» не выбран — PROPOSED
`03` §3: «ограничивается политикой последовательной обработки»; `05` §6: «не более одного run в SENT/PROCESSING». Механизм (advisory lock vs partial unique index `ON conversations WHERE run IN ('SENT','PROCESSING')`) не выбран. Влияет на этап 6, тест G-конкурентности «AI response одновременно с Handoff» (`09` §3).

### G-12. Контракт передачи вложений Bot ↔ Support Hub не описан — OPEN (внутренний)
`04` §6 фиксирует направление (бот скачивает файл из Tag и передаёт в Support Hub; исходящие — через защищённый endpoint Support Hub), но не форму: push бинарника в ingress API или pull со стороны Support Hub, размер, повторная передача. Это внутренний контракт двух наших компонентов — его можно спроектировать, но нельзя взять «как есть» из бота, пока не получен его код (11.A.5, 8).

### G-13. Суб-модель конечного пользователя: MVP-поведение не зафиксировано — OPEN
`users` / `user_identities` / `corporate_accounts` описаны (`03`), но сценарий связывания (11.C) открыт. Для MVP не определено: создаётся ли профиль пользователя автоматически из `user_id` Tag при первом сообщении (рекомендация — да, без подтверждённой корп-привязки) — предложение P-06.

## C. Риски реализации

### R-01. Внешние контракты неизвестны
Реальный API AI Orchestrator — `D-029 OPEN`; код и внутренний API существующего бота не переданы (11.A.5, 8). Все proposed endpoints в `04`/`05`/`13` — проектные эскизы. Адаптеры строятся через anti-corruption слой; до получения контрактов этапы 5–6 можно готовить только тестовыми фейками.

### R-02. Безопасность callback Tag не подтверждена
11.A.1–2: механизм аутентификации и retry-семантика неизвестны. Критичность признана в `11` §«Критичность»: без ответов нужен durable inbox у бота + сервисная авторизация Bot → Support Hub + rate limiting + строгая схема. Это компенсирующие меры, а не полная замена.

### R-03. Отсутствие Docker/Node в рабочем окружении
Интеграционные тесты на реальном PostgreSQL (`09` §3), `docker compose config`, frontend lint/typecheck/build — невыполнимы на текущей машине. Bootstrap-этап будет иметь частично проверяемые критерии, пока окружение не установлено.

### R-04. UNKNOWN-результаты отправки в Tag
`04` §7: сетевой timeout не отличим от «пост создан». Нужны статус `UNKNOWN`, reconciliation и идемпотентные повторы — подтверждено, но реализация зависит от возможностей бота (есть ли запрос статуса по delivery ID — 11.A.8).

### R-05. Поздний AI-ответ после Handoff
Схема защиты через `state_version` (`05` §6) согласована, но нет гарантии отмены уже отправленного сетевого ответа — публикацию нужно отсекать на стороне Support Hub и бота максимально близко к отправке. Требуется обязательный конкурентный тест (`09` §3).

### R-06. Несовпадение подсчёта таблиц при реализации
`03` заявляет 34 таблицы. При канонизации DDL (этап 3) количество может измениться (например, уточнение delivery states в `messages`, добавление UNIQUE `(id, user_id)` под составной FK). Это ожидаемо; правило — вести сверку этапа 3 с каталогом `03` и не копировать эскизный SQL из проектных обсуждений (`03` §5).
